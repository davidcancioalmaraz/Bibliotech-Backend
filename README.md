# BiblioTech Backend

Backend for a library management system for books and loans.

## Stack

| Layer     | Choice                                 |
|-----------|----------------------------------------|
| Runtime   | Node.js 24                             |
| Framework | NestJS 12 (Express)                    |
| Language  | TypeScript 6                           |
| Database  | PostgreSQL 18 with TypeORM 1           |
| Tests     | Vitest 4 (unit and e2e)                |
| Tooling   | oxlint, Prettier, pm2 in the container |

The project is **pure ESM** (`"type": "module"`, `module: nodenext`). Relative imports therefore carry a `.js` extension
even when the file on disk is a `.ts`
one:

```ts
import { BookModule } from './book/book.module.js'
```

## Requirements

- Node.js 24 or newer
- Docker with Docker Compose

## Getting started

### With Docker Compose

Brings up the API and the database. Pending migrations are applied on start.

```shell
cp .env.example .env
docker compose up -d
```

The API listens on http://localhost:3000.

### Locally, with the database in Docker

```shell
npm install
cp .env.example .env
docker compose up -d database
npm run migration:run
npm run start:dev
```

## Environment variables

Copy `.env.example` to `.env`. The file is read by `src/database/data-source.ts`
through Node's native `process.loadEnvFile()`, so no `dotenv` dependency is involved.

| Variable            | Default               | Description                               |
|---------------------|-----------------------|-------------------------------------------|
| `PORT`              | `3000`                | Port the application listens on           |
| `DB_HOST`           | `localhost`           | Database host — `database` inside Compose |
| `DB_PORT`           | `5432`                | Database port                             |
| `DB_USERNAME`       | `postgres`            | Database user                             |
| `DB_PASSWORD`       | `bibliotech-password` | Database password                         |
| `DB_DATABASE`       | `postgres`            | Database name                             |
| `DB_MIGRATIONS_RUN` | `false`               | Apply pending migrations on start         |
| `DB_LOGGING`        | `false`               | Log every SQL statement                   |
| `SEED_BOOK_COUNT`   | `25`                  | Books generated by the seeder             |
| `SEED_FRESH`        | `false`               | Truncate `book` before seeding            |
| `SEED_FAKER_SEED`   | —                     | Fix faker's seed for a reproducible set   |

`POSTGRES_VERSION` (default `18.6-alpine`) and `TZ` (default `America/La_Paz`)
are only consumed by `docker-compose.yml`.

## Database

The connection lives in `src/database/data-source.ts`, the single source of truth shared by the application
(`TypeOrmModule.forRoot`) and the TypeORM CLI.

Two things to keep in mind when working on it:

- `synchronize` is always disabled. The schema is owned by the migrations.
- Entities are registered explicitly in the `entities` array. A new entity has to be added there before TypeORM picks it
  up.

### Migrations

Migration files live in `src/database/migrations/` and are compiled into `dist`
by `npm run build`.

- Generate a migration from the difference between the entities and the database

  ```shell
  npm run migration:generate --name=CreateBookTable
  ```

- Create an empty migration

  ```shell
  npm run migration:create --name=SeedInitialData
  ```

- Apply the pending migrations

  ```shell
  npm run migration:run
  ```

- Revert the last applied migration

  ```shell
  npm run migration:revert
  ```

- List the migrations and their state

  ```shell
  npm run migration:show
  ```

> `--name=` is required by `migration:generate` and `migration:create`. Without
> it the command stops with `Missing --name=<MigrationName>` instead of writing
> the file to the wrong place.

Migration files must stay inside `src/database/migrations/`. That directory is the only path the data source looks at,
so a file left anywhere else is silently never executed.

Any other CLI command is available through the `typeorm` script, which already points at the data source:

```shell
npm run typeorm -- migration:generate src/database/migrations/CreateBookTable
```

Under Docker Compose the backend applies the pending migrations on start, through `DB_MIGRATIONS_RUN=true`.

### Seeders

Seeding is handled by [`typeorm-extension`](https://www.npmjs.com/package/typeorm-extension)
with the standard *factory + seeder* pair, and the rows themselves are generated
with [`@faker-js/faker`](https://fakerjs.dev) in Spanish — there is no static
fixture file.

```
src/database/
  seed.ts                 Opens the data source and calls runSeeders()
  seeds/
    faker.ts              The faker instance, locked to Spanish
    locale/es-libros.ts   Spanish book vocabulary and title/synopsis templates
    book.factory.ts       Builds one random Book
    book.seeder.ts        Persists SEED_BOOK_COUNT books through the factory
```

#### Everything comes out in Spanish

faker ships no Spanish data for books: the official `es` locale covers `person`,
`company` and `location`, but `book.*` and `word.*` fall back to English and
`lorem` is always Latin. So the vocabulary is supplied as **an extra locale layer
of our own**, `esLibros`, and the seeding instance is built from it:

```ts
export const faker = new Faker({ locale: [esLibros, es, base] })
```

faker resolves the layers left to right, so `esLibros` wins and anything it does
not define (names, cities, dates) comes from the official `es` locale. `en` is
deliberately **left out of the chain**: a module with no data in any of the three
layers throws a `FakerError` instead of silently returning English text.

`esLibros` defines `book.genre` (literary genres), plus `book.title` and
`book.publisher` as **templates** — `'El {{word.noun}} de {{location.city}}'` —
which the factory resolves with `faker.helpers.fake()`. Titles are therefore
combinatorial rather than a fixed list: *"El faro invisible"*, *"Cartas desde
Toledo"*, *"Crónica del viaje"*. Synopses work the same way, from
`plantillasDescripcion` in the same file.

To widen the vocabulary, add entries to the arrays in
`src/database/seeds/locale/es-libros.ts`. Nouns are all masculine and adjectives
masculine singular, so the templates agree in gender without special cases.

Run it:

```shell
npm run seed
```

The script compiles first (`nest build`) and then executes `dist/database/seed.js`,
so it reuses the same `dataSourceOptions` and the same `.env` as the application.

Three environment variables tune a run:

- `SEED_BOOK_COUNT` — how many books to insert (default `25`).
- `SEED_FRESH=true` — `TRUNCATE ... RESTART IDENTITY` on `book` before inserting,
  so the table is rebuilt from scratch with ids starting at 1.
- `SEED_FAKER_SEED=<n>` — fixes faker's seed, so the same command always produces
  the same set of books. The ids may still be assigned in a different order, since
  `saveMany` inserts concurrently.

```shell
SEED_FRESH=true SEED_BOOK_COUNT=100 npm run seed
```

The seeder is **not** idempotent by design: running it again appends another batch
of random books. `code` is generated as `BT-` plus eight random alphanumerics, so a
second run does not collide with the unique constraint. Use `SEED_FRESH=true` to
reset instead of accumulating.

Inside Compose, the compiled tree sits at the workdir root of the image, so the
command drops the `dist/` prefix:

```shell
docker compose exec bibliotech-backend node database/seed.js
```

Both `typeorm-extension` and `@faker-js/faker` are runtime `dependencies` for that
reason — the `runner` stage installs with `npm install --production`.

## Docker

`docker-compose.yml` defines two services:

- **database** — PostgreSQL, published on `127.0.0.1:5432`, persisted in the
  `database_data` volume, with a `pg_isready` healthcheck.
- **bibliotech-backend** — the API, published on `PORT` (`3000` by default). It waits for the database to be healthy and
  applies pending migrations on start.

Changing `DB_USERNAME` or `DB_DATABASE` on an existing installation requires recreating the volume:

```shell
docker compose down -v
docker compose up -d
```

PostgreSQL only runs `initdb` on an empty data directory, so without that step the new user or database is never created
and the application cannot connect.
